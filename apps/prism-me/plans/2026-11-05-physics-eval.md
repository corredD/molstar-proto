# Physics engine for prism-me "draw mode": is jure/webphysics a fit?

Date: 2026-11-04. Read from a clone of jure/webphysics at `96b043c` (2026-04-16). The clone is read-only, and no install
was run. prism-me was read at `10ebe1416`, in `~/molstar-prism-me`.

## 1. Verdict

1. **Do not adopt webphysics as the engine.** It is a Chrome-only prototype tied to three.js. Its hard limit is 65,536
   bodies, and it has no compound bodies. It has had no commits since 2026-04-16.
2. Its O(n²) pair bitset and its per-body contact slots use about 390 MB of GPU memory at 32k bodies. One 2–10-bead
   protein costs 2–10 bodies, so it cannot reach "thousands to millions of instances".
3. **Use it as a reference.** It is MIT-licensed, and its WGSL LBVH, radix sort and AVBD solver are good reading.
4. **Recommended path:** write a small custom bead solver on Mol*'s own `ComputeContext`. It uses a uniform grid hash
   with PBD and shape matching, so each protein is a rigid group of beads. The drawn instances are dynamic, and the
   existing model is a static obstacle grid. On WebGL2, a CPU fallback runs the same algorithm in TypeScript in a
   worker; Rapier is the alternative if better rigid behaviour is needed there.
5. _*The real bottleneck is in Mol*, not in the engine._* Per-frame instance updates go through a CPU transform and
   instance-grid rebuild. For more than about 100k moving instances, the solver must write transforms on the GPU,
   directly into the culler input.

Other options, briefly:

- **cannon-es** (MIT, last push 2024-01) and **Oimo.js** (MIT, last push 2021-07) are inactive and slower than Rapier.
  Skip them.
- **JoltPhysics.js** (MIT, active 2026-10) is a credible alternative to Rapier for the CPU path. It also supports
  compound shapes. It is a larger WASM file.
- **dimforge/nexus** ("rapier on the GPU", Apache-2.0, active 2026-11) is still under heavy development. Its shaders are
  Rust-GPU compiled to SPIR-V, and it has no JS or WGSL route for browsers today. Watch it.
- LAMMPS-style coarse-grained JS ports: none credible were found. A bead model with PBD and soft repulsion is the same
  idea, done in a simpler way.

## 4. Recommended path

**prism-me facts the plan depends on:**

- `ParticleList` stores `coordinates` (xyz) and optional `rotations` (quaternions) as `Float32Array`.
  `getParticleTransforms` builds a mat4 for each instance and **caches it by list object**
  (`packages/model/src/model/particles/particle-list.ts:57-123, 220-296`). Changing `coordinates` in place therefore has
  no effect on rendering.
- Each update runs `createTransform` then `updateTransformData`. This is a CPU loop that copies 16 floats per instance
  and then runs `calcInstanceGrid` (a spatial re-sort for culling) over **all** instances
  (`packages/graphics/src/geo/geometry/transform-data.ts:51-174`). The WebGPU merged culler then reads that CPU
  `aTransform` and the cell grid (`packages/graphics/src/gl/renderable/merged-culler.ts:54,247,398`).
- The planned dynamics design (memory note `particle-dynamics-plan`) assumes "Mol* is WebGL2-only, no compute". **That
  is now stale**, because prism-me runs on WebGPU with `ComputeContext` kernels
  (`packages/graphics/src/gl/compute.ts:176`, `gl/webgpu/compute.ts`). The full plan file
  `~/.claude/plans/rustling-finding-flame.md` **no longer exists**; only the memory note remains.

**Path, in lanes:**

| Lane                   | What                                                                                                                                                                                                                                                                                                | Size (lines, not counting tests) |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| L1 – draw seam         | Draw mode creates instances into a dynamic `ParticleList` layer: a separate small list for "drawn" instances, kept apart from the big static list. Add an in-place transform update path that bypasses the cache, updates `aTransform` for that list only, and calls `requestDraw`. No physics yet. | ~300–400                         |
| L2 – CPU bead solver   | TypeScript, run in a worker. Bead templates per target (2–10 spheres from the target's coarse model). Uniform grid hash, PBD sphere–sphere separation, and per-instance shape matching to recover the rigid transform. The static model is loaded as a static grid. This is also the WebGL2 path.   | ~500–700                         |
| L3 – GPU bead solver   | The same algorithm as `ComputeContext` kernels: hash, counting sort (reusing `prefix-sum.ts`), contact projection, shape matching and transform write. Validate it against L2 on the same seed.                                                                                                     | ~700–1000 (WGSL + TS)            |
| L4 – GPU → culler seam | Let the merged culler take a GPU-resident transform buffer for a dynamic layer, so there is no readback and no CPU `calcInstanceGrid` each frame. Treat the dynamic layer as a single coarse cell, or rebuild its grid every K frames.                                                              | ~300–500, touches core graphics  |

Total: about 1.8–2.6k lines in 4 lanes. L1 and L2 alone give a usable draw mode with collisions up to roughly 10⁴–10⁵
dynamic beads. L3 and L4 are needed only for the "millions" goal. If L2 needs real rigid-body behaviour (friction,
stacking) rather than coarse non-overlap, Rapier with ball-compound colliders in a worker can replace L2. It costs about
300 lines of glue, plus the WASM dependency.

## 5. Risks

- _*The Mol* update path is the ceiling._* Without L4, every engine is limited by the CPU `updateTransformData` and
  `calcInstanceGrid` over the moving list. The drawn layer must stay a separate, small `ParticleList`. Rebuilding the
  2M-instance list each frame would break interactivity.
- **The L4 seam is in core graphics.** The merged culler is shared by all representations, so a change there needs
  Alex-style review and a WebGL2 no-op path.
- **PBD is not dynamics.** It gives non-overlap and settling, not physically correct diffusion or crowding. That is
  enough for drawing, but it must not be presented as simulation.
- **Bead templates.** Each target needs a 2–10-sphere coarse model (for example, k-means on atoms, or a cellPACK `radii`
  / `positions` entry if present). Missing templates fall back to one sphere.
- **GPU memory and limits** on low-end or mobile GPUs. A uniform grid over a whole cellPACK cell is large, so use a
  hashed grid of fixed size rather than a dense one.
- **webphysics as a reference only.** If code is copied (for example the OneSweep radix sort), keep the MIT notice. The
  OneSweep sorter (`src/lvbh/sorting/`) comes from b0nes164/GPUSorting (MIT, Thomas Smith); keep that notice too.
- **Rapier numbers are estimates.** Measure them on Ludo's M1 before choosing between Rapier and the custom CPU twin for
  L2.
