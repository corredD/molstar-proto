## Summary

- **The known undo throw: root cause found and reproduced.** It is not specific to undo or to cryoet. Mol*'s
  `State._updateTree` emits `events.changed` while `_inUpdate` is still true (core `state/state.ts:488`, cleared at
  `:436`). The volume hierarchy manager subscribes before the particle one (plugin `context.ts:240` vs `:243`), so it
  syncs first and fires `behaviors.selection`. prism-viewer's scene `sync` (`sources/scene.ts:1821`) then reads
  `particles.hierarchy.current`. That getter calls `sync(false)`, which returns early during `inUpdate`
  (`particles/hierarchy.ts:54`), so it returns the hierarchy from before the update. The removed list is still in it.
  `particleListData` (`scene.ts:3264`) then calls `getDecoratorRoot`, which reads `tree.children.get(removedRef)`
  (undefined) and its `.size` throws (`immutable.ts:259`). A load never throws, because a stale hierarchy that lacks a
  new list is harmless; only a removal leaves a dangling ref. The same throw happens on a plain
  `build().delete(volume).delete(list).commit()` with no history. The scene recovers: `SceneChangeLog.batch` has a
  `finally`, and a later load lists its rows.
- **New must-fix: a slow EMPIAR load blocks the whole viewer's history queue.** Top-level history runs are serialized.
  An `empiar.load` downloads from EBI inside its step: 2–4 h for the card's default pick, 1–2 min for one 12 MB STAR.
  Until it finishes, every other undoable operation waits. Proven with a gated fetch.
- **Duplication:** about 7 blocks are copied between `portal.ts` and `empiar.ts`, plus the card scaffolding. `empiar.ts`
  now imports six private helpers that it made public in `portal.ts`. A shared `load-steps.ts` would hold them.
- **Inconsistencies:**
  - "MB" means 10⁶ bytes on the portal and MiB on EMPIAR, and EMPIAR's 512e6-byte guard contradicts its own labels.
  - The portal card always sends `large: true`; the EMPIAR card asks first.
  - A named file that cannot load fails an EMPIAR load; on the portal the same case is a warning.
- **Card races:**
  - On both cards, a load in flight loses its result when the pick changes.
  - The portal card never clears an old error.
  - When a portal read fails, the portal card shows the new select but Load sends the old dataset (EMPIAR fixed this as
    review S6; the portal did not get the fix).
